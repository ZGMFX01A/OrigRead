## Bug 与修复

### BUG-01 / P1：STAGING 业务写入遗漏同步事件

两端 runtime 与 Outbox allocator 的可写状态未包含 STAGING。快照安装后等待 Tail 的窗口内，业务修改成功，但没有 Outbox，后续无法传播。

修复：两端统一允许 STAGING 的持久化 mutation capture 和 Outbox 分配；保留原事务边界。Desktop 安装完成后的生命周期同时纠正为 STAGING。

回归：Android `SyncOutboxAllocatorTest.stagingMutationIsDurablyCaptured`；Desktop `sync-runtime-foundation.test.ts`。修复前失败，修复后通过。

### BUG-02 / P1：待处理首页被阻塞后，后续可执行操作饥饿

Android 与 Desktop 原来每次只读固定数量 PENDING。缺前序或依赖的记录占满首页时，后页可用操作永远没有机会执行。

修复：按复合游标遍历后续页，跳过当前无法应用的记录，成功应用达到 limit 时停止；维持原有逐 Actor 连续序号及授权检查。

回归：Android `SyncApplyFairnessTest`；Desktop `sync-ingestion-contract.test.ts` 的跨 Actor 依赖场景。修复前失败，修复后通过。

### BUG-03 / P1：发布新检查点后，历史合法快照被错误拒绝

安装器把快照引用的 AuthStabilityCheckpoint 强制当成最新检查点。当账本已有 C2，但仍可用的快照引用 C1 时，合法恢复失败。

修复：在已验证的授权账本中按快照声明的检查点 ID、类型、Space 精确查找；继续验证 accepted coverage、恢复快照授权及 commitment，不放宽签名检查。

回归：Android `historicalCheckpointStillAuthorizesItsSnapshot`；Desktop 快照安装测试的 historical checkpoint 参数分支。使用真实签名 C1/C2 验证。

### BUG-04 / P1：仅有快照覆盖、没有保留日志时不进入恢复

对端 snapshot coverage 比本地新，但 retained ranges 为空。Android 原抛错位置在恢复捕获之外；Desktop 原路径跳过恢复，导致缺失 baseline 不能补齐。

修复：在共用拉取循环中识别 snapshot-only gap，并在现有 BASELINE_REQUIRED 恢复处理范围内触发快照查找。

回归：两端 `snapshotOnlyCoverageEntersBaselineRecovery` 对应 SessionCoordinator 测试；断言到达快照恢复入口而非发起不可用日志范围请求。

### BUG-05 / P1：STAGING 重装同一快照覆盖安装后的本地修改

独立复核发现：同 bundle/root 的重入仍重新物化旧 CONFIG；Android 扩展投影也会重物化。最初保存的恢复 capsule 不包含安装完成后的新写入，因而可能恢复旧值。

修复：使用现有 recovery capsule 表持久化本地安装完成记录，包含 bundle、rootHash、实际 installedLanes；与 STAGING 状态在事务中一同写入。相同 bundle/root 且所需范围已安装时幂等返回，不重复投影；REBASE_PREPARE 保留修复路径。不能仅按完整 manifest 判断部分 lane 已安装。

回归：两端先安装 CORE_META/AUTH 再扩展完整范围，确认会补装 CONFIG；完成后修改配置，再重装相同快照，确认不覆盖新值。故障版本重入测试失败，修复后通过。

### BUG-06 / P1：快照安装后断线，新会话无法恢复 ACTIVE

原 stagedSnapshotBundleId 仅保存在一次 run 的局部变量中。安装后断线，再次同步利用已持久化 coverage 继续拉 Tail，无需重新安装，就永远不会调用激活。

修复：SessionCoordinator 从持久化安装记录恢复待激活 bundle，并在 Tail、coverage 和依赖检查后进入原 activateAfterTail 路径。Android 同时恢复绑定账号。

回归：两端用已持久化 STAGING 与安装记录创建新会话，验证无再次安装也调用激活。修复前失败，修复后通过。

### BUG-07 / P2：按散列 operationId 分页造成连续日志近似平方级扫描

BUG-02 初版修复采用散列 ID keyset。散列顺序随机打散 sequence，顺序应用时大量记录反复 deferred。独立复核使用实际 ID 算法模拟，1,000 条连续日志需要 506 轮、249,865 次记录访问。

修复：两端改用 `(replicationLaneId, actorIncarnationId, sequence)` 复合 keyset，兼顾跳过阻塞页与同 Actor 顺序执行。

回归：Desktop 100 条连续日志单次 applyPending 全部执行；原散列排序仅执行 2 条。Android 公平性测试同步使用复合 cursor，Room 查询经编译验证。

## 第二轮复核补充：BUG-08 / P1，Android 未完成跨库安装被进度判断跳过

主库事务已推进 coverage，而 AI_HISTORY 投影、保留 Tail 或 READY 提交尚未完成时退出，账号停在 REBASE_PREPARE。旧会话入口只恢复 STAGING；由于 received 已追上对端，新会话可能不再安装快照而返回成功。

修复：在任何物化之前，将已验证的完整 bundle/shards、原始 selected lanes、root、安装前 coverage 和 STARTED 状态与 REBASE_PREPARE 原子持久化。新会话在 preflight 应用及进度上报之前恢复该安装，先排空两端业务投影的本地 capture 并签名，使用保存的范围重新执行完整安装。恢复时合并安装前与当前 coverage，重新收集现存有效已签名 Tail，不再只回放旧 capsule ID。未完成时拒绝换 bundle/root 或扩大范围，完成后才允许下一次安装扩大范围。READY 仍与 STAGING 同事务发布。

验证：`interruptedMainCommitPreservesExactInstallScope` 在主库提交后模拟中断，核对 STARTED 范围，拒绝错误范围并允许同范围恢复；`interruptedProjectionReplaysNewLocalOperations` 注入扩展投影失败，恢复时验证扩展投影完成且重放期间新增 CONFIG operation；`newSessionResumesUnfinishedInstallBeforeTrustingCoverage` 验证新会话先恢复安装，失败时不上报 applied，成功后继续激活。前两项问题信号（持久开始记录缺失、新会话未恢复）已在修复前实际运行失败。

第二轮独立复核已确认 BUG-05/06/07 resolved；本项是新增 blocking，完成回归后进入同一 reviewer 的第三轮复核。
